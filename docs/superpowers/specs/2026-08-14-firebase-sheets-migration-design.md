# Миграция «Учёт проката» на Firebase/Firestore + синк в Google Sheets + GitHub

## Контекст

Сейчас `uchet-prokat.html` — одностраничное приложение (vanilla JS, встроенный Chart.js, без сборки), хранящее все данные в `localStorage` браузера. Это значит: данные видны только на одном устройстве/браузере, ничего не бэкапится, доступа с телефона к тем же записям, что на компьютере, нет.

Цель: сделать данные доступными с любого устройства (общая облачная база), продублировать записи в Google Таблицу для внешнего архива/отчётности, и опубликовать код на GitHub с бесплатным хостингом фронтенда.

## Согласованные решения

- **Авторизация**: один общий логин (email/пароль в Firebase Auth), создаётся вручную один раз в консоли Firebase. Публичной регистрации нет.
- **Синк с Google Sheets**: только выгрузка Firestore → Sheets, автоматически при каждом добавлении записи. Таблица — **журнал добавлений** (append-only): редактирование/удаление записи в приложении **не** меняет и не удаляет соответствующую строку в таблице.
- **Реалтайм**: изменения на одном устройстве должны мгновенно появляться на другом без перезагрузки страницы.
- **Данные**: миграция старых demo/локальных данных не требуется — начинаем с чистой базы в Firestore.
- **Хостинг фронтенда**: GitHub Pages, репозиторий **публичный** (бесплатный тариф Pages требует public repo; сами данные в репозиторий не попадают — только код интерфейса и публичный Firebase Web config, что безопасно и стандартно для Firebase).
- **Фронтенд остаётся одним HTML-файлом**, без сборщика — Firebase SDK подключается через ESM CDN-импорты (`<script type="module">`). Обоснование: сохраняет текущую простоту («открыл файл — работает»), не требует build-шага в CI для деплоя на Pages.
- **Синк в Sheets реализован через Firestore-триггер** (`onDocumentCreated` в Cloud Functions), а не прямой вызов из фронтенда. Обоснование: триггер надёжнее — у Firebase есть автоматический ретрай при сбое, запись в таблицу не потеряется даже если у пользователя после сохранения в Firestore пропадёт связь.

## Архитектура

```
Браузер (uchet-prokat.html, GitHub Pages)
   │  Firebase Auth (email/pass) + Firestore SDK (onSnapshot realtime)
   ▼
Firestore (transactions, sourceRecords, settings/config)
   │  onDocumentCreated trigger
   ▼
Cloud Function (Blaze plan) → Google Sheets API → Google Таблица (append-only журнал)
```

### Firestore — модель данных

- `transactions/{autoId}`: `{date, type: 'income'|'expense', status, category, qty, amount, payment, source, client, prepayment, createdAt: serverTimestamp}` — повторяет текущую структуру записи из `uchet-prokat.html`.
- `sourceRecords/{autoId}`: `{date, source, qty, createdAt}`.
- `settings/config` (один документ): `{equipmentTypes: [], otherIncomeCategories: [], expenseCategories: [], paymentMethods: [], sources: []}` — редактируемые пользователем списки категорий, ранее хранившиеся в localStorage. Меняются на одном устройстве — подтягиваются на другом через `onSnapshot`.

### Firebase Auth

- Один пользователь email/пароль, создаётся вручную в консоли Firebase (не через код, не self-service).
- Фронтенд: экран логина показывается, если `onAuthStateChanged` не даёт активного пользователя; после успешного входа показывается основной интерфейс. Сессия сохраняется локально (Firebase persistence) — повторный вход не нужен на том же браузере.

### Firestore Security Rules

```
match /{document=**} {
  allow read, write: if request.auth != null;
}
```
Простое правило, т.к. логин один общий — разделения прав по пользователям не требуется.

### Cloud Function (Sheets sync)

- Триггер: `onDocumentCreated` на `transactions/{id}` и на `sourceRecords/{id}` (два триггера или один общий на `{collection}/{id}` с ветвлением по имени коллекции).
- Действие: формирует строку значений и вызывает `spreadsheets.values.append` Google Sheets API. Три вкладки в таблице: «Доходы» (документы `transactions` с `type: 'income'`), «Расходы» (`transactions` с `type: 'expense'`), «Источники» (`sourceRecords`) — выбор вкладки по коллекции и полю `type`, без смешения типов в одном листе.
- Аутентификация к Google Sheets API: сервис-аккаунт Google Cloud, JSON-ключ хранится в Secret Manager Cloud Functions (`firebase functions:secrets:set`), **не коммитится в репозиторий**. Целевая Google Таблица расшаривается на email сервис-аккаунта с правом редактирования.
- Ошибки записи в Sheets (сеть, rate limit) не блокируют и не откатывают запись в Firestore — Firestore уже сохранил данные до срабатывания триггера. Ошибки логируются в Cloud Functions Logs; при необходимости включается стандартный ретрай триггера.

### Хостинг и репозиторий

- Новый **публичный** git-репозиторий на GitHub, код `uchet-prokat.html` (+ вспомогательные файлы конфигурации Firebase/Functions) кладётся в него.
- GitHub Pages раздаёт статику прямо из ветки репозитория — build-шаг не нужен.
- Cloud Function деплоится вручную командой `firebase deploy --only functions` (CI для этого не настраивается в рамках этой миграции — вне текущего скоупа).

### Влияние на существующий функционал

- Кнопка **«Очистить все данные»** теперь означает пакетное удаление документов `transactions`/`sourceRecords` в Firestore. Google-таблицу кнопка не трогает (осознанно — таблица архивный журнал, не текущее состояние).
- Все текущие `load()/save()`-функции на localStorage заменяются на Firestore-чтение через `onSnapshot` (реалтайм-подписка) и запись через `addDoc`/`updateDoc`/`deleteDoc`.

## Тестирование

1. Сначала — Auth + Firestore realtime на бесплатном Spark-плане (без Cloud Function): проверить логин, добавление/редактирование/удаление записи, синхронизацию между двумя открытыми вкладками/устройствами без перезагрузки.
2. Переход на Blaze-план, деплой Cloud Function, тестовая Google Таблица: проверить, что при добавлении дохода/расхода/источника строка корректно дописывается; проверить, что редактирование/удаление записи в приложении **не** меняет таблицу.
3. Деплой фронтенда на GitHub Pages, проверка полного цикла с телефона (отдельное устройство, вход под тем же общим логином).

## Вне скоупа этой миграции

- CI/CD для автодеплоя Cloud Function при пуше в GitHub.
- Двусторонняя синхронизация или синхронизация правок/удалений с Google Sheets.
- Множественные индивидуальные логины/роли пользователей.
- Перенос старых demo-данных (начинаем с чистой базы).
